# Лабораторная работа №5

Тема: Проектирование кэша/сессий и реализация операций Redis

Вариант 3 - Библиотечная система

## Цель

Научиться проектировать Redis-хранилище для кэша и пользовательских сессий: ключи, структуры данных, TTL, инвалидирование кэша, и освоить основные команды Redis.

## Предметная область

Библиотека. Читатели ищут книги в каталоге и смотрят карточки книг, библиотекари выдают и принимают книги. Основные данные (книги, читатели, выдачи) лежат в основной БД, Redis стоит рядом и хранит кэш карточек книг и сессии.

Пользователи: читатель, библиотекарь, администратор.

Все данные учебные, id читателей и сессий выдуманные.

Все команды по порядку в commands.txt.

## Анализ требований

| Данные | Операция | Частота | Кэшировать? | TTL | Причина |
|---|---|---|---|---|---|
| Карточка книги (название, автор, полка) | чтение | высокая | да | 600 с | почти не меняется |
| Кол-во свободных экземпляров | чтение/запись | высокая | ограниченно | 30 с | меняется при каждой выдаче |
| Сессия | чтение/запись | высокая | хранится в Redis | 1800 с | временные данные |
| Последние просмотренные книги | чтение/запись | средняя | хранится в Redis | без TTL, до 5 элементов | не критично если потеряется |
| Просмотры книги | запись | высокая | хранится в Redis | без TTL | счетчик |
| Выдачи и возвраты | запись | средняя | нет | - | нужна точность, только основная БД |

Паттерны доступа:
1. получить карточку книги по id
2. получить сессию по id
3. проверить сколько осталось жить сессии
4. получить последние просмотренные книги читателя
5. узнать сколько читателей сейчас онлайн
6. узнать кол-во просмотров книги

## Выбор модели

| Критерий | Основная БД | Redis |
|---|---|---|
| Постоянное хранение | подходит | не для этого |
| Быстрое чтение по ключу | зависит от индексов | подходит |
| TTL | надо делать самому | встроен |
| Сессии | можно | удобно |
| Кэш | можно | для этого и нужен |

В основной БД остаются книги, читатели, выдачи, штрафы. В Redis только то, что можно потерять и восстановить: кэш карточек, сессии, счетчики, списки последних просмотров. Redis тут и кэш и session store одновременно.

## Ключи

Шаблон: `<тип>:<сущность>:<id>`

| Ключ | Тип | Назначение | TTL |
|---|---|---|---|
| cache:book:301 | Hash | карточка книги | 600 |
| cache:book:303 | Hash | карточка книги | 600 |
| cache:book:304 | Hash | карточка книги | 600 |
| cache:book:305 | Hash | карточка книги | 600 |
| cache:book:303:available | String | свободные экземпляры | 30 |
| session:s001, s002, s003 | Hash | сессия | 1800 (библиотекарь 900) |
| recent:reader:1001 | List | последние просмотренные книги | нет, обрезается LTRIM |
| book:301:views | String | счетчик просмотров | нет |
| online:library | Set | кто сейчас онлайн | нет |

- Hash для книги и сессии, потому что это объект с полями, можно читать и менять одно поле
- String для счетчика, потому что есть INCR
- List для последних просмотров, потому что важен порядок
- Set для онлайна, потому что один пользователь не должен быть там два раза

## Тестовые данные

```
HSET cache:book:301 book_id 301 title "Мастер и Маргарита" author "Михаил Булгаков" category "роман" year 2015 shelf "A-04"
EXPIRE cache:book:301 600
HSET cache:book:303 book_id 303 title "Чистый код" author "Роберт Мартин" category "программирование" year 2019 shelf "C-11"
```

Всего получилось 4 карточки книг, 3 сессии, 3 счетчика, 2 списка, 1 множество из 4 элементов.

## Сессии

```
HSET session:s001 user_id 1001 role reader language ru last_section catalog
EXPIRE session:s001 1800
HSET session:s002 user_id 1002 role reader language kk last_section book:305
EXPIRE session:s002 1800
HSET session:s003 user_id 501 role librarian language ru last_section returns
EXPIRE session:s003 900
```

## Инвалидирование

Книгу 305 переставили на другую полку. В основной БД shelf = B-03, а в кэше еще старое значение:
```
> HGET cache:book:305 shelf
"A-12"
> EXISTS cache:book:305
(integer) 1
> DEL cache:book:305
(integer) 1
> EXISTS cache:book:305
(integer) 0
> HGETALL cache:book:305
(empty array)
```
Следующий запрос - cache miss, приложение идет в основную БД и кладет в кэш новое:
```
> HSET cache:book:305 book_id 305 title "Абай жолы" author "Мухтар Ауэзов" category "роман" year 2018 shelf "B-03"
(integer) 6
> EXPIRE cache:book:305 600
(integer) 1
> HGET cache:book:305 shelf
"B-03"
```

1. При следующем запросе будет cache miss
2. Актуальные данные берутся из основной БД
3. Да, надо снова положить в Redis, иначе каждый запрос пойдет в БД
4. TTL тот же, 600 секунд
5. Если не инвалидировать, читатель до 10 минут будет видеть старую полку и искать книгу не там

Кэш книги инвалидирую через DEL после изменения в основной БД, а TTL 600 остается как страховка если DEL не дошел.

Что можно кэшировать про доступность экземпляров: общее число экземпляров можно, оно почти не меняется. Число свободных можно только на короткое время (30 секунд) и только для показа в каталоге. При самой выдаче проверять надо по основной БД, иначе две выдачи одного экземпляра.

## Перезапись ключа и TTL

```
> SET lab5:ttl "first" EX 120
OK
> TTL lab5:ttl
(integer) 120
> SET lab5:ttl "second"
OK
> TTL lab5:ttl
(integer) -1
```
Обычный SET стирает TTL, ключ стал вечным. Чтобы так не было, надо либо снова указывать EX, либо KEEPTTL:
```
> SET lab5:ttl "third" EX 120
OK
> SET lab5:ttl "fourth" KEEPTTL
OK
> GET lab5:ttl
"fourth"
> TTL lab5:ttl
(integer) 120
```
То есть TTL надо продумывать при каждой записи в кэш, а не один раз при создании.

## Стратегии TTL для карточки книги

| TTL | Cache hit | Нагрузка на БД | Риск устаревания |
|---|---|---|---|
| 30 с | ниже | выше | низкий |
| 5 мин | средний | средняя | средний |
| 1 час | выше | ниже | высокий |

Для карточки книги выбрал 10 минут + DEL при изменении. Карточка меняется редко, а если поменялась то DEL сразу убирает старое. Для свободных экземпляров 30 секунд.

## Анализ решения

1. Redis выбран потому что нужен быстрый доступ по ключу и автоматическое удаление по TTL
2. В Redis карточки книг, сессии, счетчики просмотров, списки последних просмотров, онлайн
3. В основной БД остаются книги, читатели, выдачи, возвраты, штрафы
4. Hash для объектов с полями, String для счетчиков, List для истории, Set для уникальных пользователей
5. Ключи по шаблону тип:сущность:id, например cache:book:301
6. 600 с для карточки потому что она редко меняется, 1800 с для сессии это обычные полчаса неактивности, 30 с для свободных экземпляров потому что они меняются часто
7. Устареть может карточка книги (полка) и число свободных экземпляров
8. DEL после изменения в основной БД плюс TTL как запасной вариант
9. При cache miss приложение читает из основной БД и записывает результат в Redis с TTL
10. При росте пользователей понадобится больше памяти, потом репликация или кластер Redis. Set online:library станет большим, SMEMBERS по нему лучше не делать, только SCARD
11. Нельзя надолго кэшировать свободные экземпляры и статус выдачи
12. Слишком большой TTL - устаревшие данные, слишком маленький - кэш почти не помогает и все запросы идут в БД

## Контрольные вопросы

1. Key-value это когда данные достаются по ключу. В Redis ключ это строка, а значение может быть строкой, хешем, списком, множеством
2. TTL это время жизни ключа. Нужен чтобы кэш не устаревал навсегда, а сессии сами удалялись
3. Cache hit - данные нашлись в Redis, cache miss - не нашлись и надо идти в основную БД
4. GET читает строку целиком, HGET читает одно поле из хеша
5. `EXPIRE key 600` ставит время, `TTL key` показывает сколько осталось
6. По session:s001 сразу понятно что это, и не будет конфликтов с другими ключами
7. Когда у объекта несколько полей и их надо менять по отдельности, и TTL один на весь объект
8. -1 значит ключ есть но без срока жизни. Для сессии плохо, она никогда не удалится
9. Пользователь будет видеть старые данные пока кэш не истечет или его не удалят
10. Redis хранит все в памяти, в нем нет сложных запросов и связей, а данные могут пропасть. Поэтому это дополнение к основной БД

## Вывод

В этой лабе я спроектировал Redis-хранилище для библиотечной системы: кэш карточек книг и сессии пользователей. Использовал четыре структуры: Hash для книг и сессий, String для счетчиков и числа свободных экземпляров, List для последних просмотренных книг и Set для пользователей онлайн. Ключи называл по шаблону тип:сущность:id. TTL ставил на кэш (600 с), на сессии (1800 и 900 с) и на свободные экземпляры (30 с), и проверил что ключ сам пропадает когда время вышло. Проблему устаревших данных решаю удалением кэша после изменения в основной БД, а TTL остается запасным вариантом. Еще увидел что обычный SET сбрасывает TTL, и для этого есть KEEPTTL. Ограничение модели в том, что Redis тут не основное хранилище: все важное (выдачи, читатели) должно быть в основной БД, а кэш можно потерять.
